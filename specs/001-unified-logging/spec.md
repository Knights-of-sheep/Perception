# Feature Specification: 日志统一管理模块（后端基础设施）

**Feature Branch**: `001-unified-logging`

**Created**: 2026-08-23

**Status**: Draft

**Input**: User description: "统一的日志管理模块，C++ 与 Python 命令层共享同一日志流，支持文件轮转与控制台输出"

## Clarifications

### Session 2026-08-23

- Q: 除项目自有代码外，Qt 与 VTK 的日志是否也重定向纳入统一日志流？ → A: 全部纳入（自有代码 + Qt 输出重定向 + VTK 日志）；VTK 日志另设独立开关（默认启用、可关闭）。
- Q: "日志可以分级控制"的控制粒度是？ → A: 每级别独立开关（DEBUG/INFO/WARN/ERROR/FATAL 各自可开/关），控制台与文件各持一组独立开关矩阵，可分别配置。
- Q: 菜单栏设置日志级别入口的呈现形态？ → A: `设置 → 日志级别 → {控制台 / 文件}` 两个子菜单，各含 5 个级别复选项（可多选），选择后立即生效并持久化。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 通过统一 API 记录日志并即时可见 (Priority: P1)

开发者在应用任意模块（C++ 层）通过统一的日志 API 写入日志，日志同时输出到控制台与日志文件。这是全功能日志体系的最小可用闭环：开发者写完日志调用即可在开发控制台立即看到输出，无需额外配置。

**Why this priority**: 这是日志系统的地基——统一 API 决定后续所有能力（轮转、过滤、Python 汇入）的挂载点。没有它，其余需求无从谈起。

**Independent Test**: 编写一段调用统一日志 API 的 C++ 代码（如 `Logger::instance().info("hello")`），运行应用后可在开发控制台看到格式化输出，且日志文件中出现同一条记录。

**Acceptance Scenarios**:

1. **Given** 应用已启动且默认配置生效，**When** 任意模块调用统一日志 API 写入一条 INFO 日志，**Then** 该日志立即出现在开发控制台，且包含时间戳、日志级别、来源模块、消息正文。
2. **Given** 控制台的 DEBUG 级别开关为关、文件侧的为开，**When** 写入一条 DEBUG 日志，**Then** 控制台不显示该条记录，文件侧正常记录。
3. **Given** 日志 API 被多线程并发调用，**When** 同时写入多条日志，**Then** 每条记录完整、无交错截断，时间顺序可依赖（线程安全）。
4. **Given** 某模块通过 Qt 的 qDebug/qWarning 输出日志，**When** 输出产生，**Then** 该记录进入统一日志流，格式与级别开关策略与统一 API 一致。

---

### User Story 2 - 日志文件按大小轮转，保留可预期的归档 (Priority: P2)

应用持续运行产生日志，单文件达到 5MB 时自动轮转，仅保留最近 3 份归档，磁盘占用可预期，不会无限增长。

**Why this priority**: 长期运行的桌面应用必须有可预期的磁盘占用；轮转是日志文件管理的最小必要能力，且独立于日志 API 本身。

**Independent Test**: 将轮转阈值临时调小（如 1KB）并写入超过阈值的日志，观察产生 `xxx.log`、`xxx.log.1`、`xxx.log.2`、`xxx.log.3` 归档；继续写入后最旧归档被删除，文件总数不超过 4（1 当前 + 3 归档）。

**Acceptance Scenarios**:

1. **Given** 当前日志文件已达到 5MB，**When** 写入下一条日志，**Then** 当前文件被轮转为归档，新内容写入新文件。
2. **Given** 已有 3 份归档，**When** 再次触发轮转，**Then** 最旧归档被删除，归档数量保持在 3。
3. **Given** 日志文件路径已配置为应用数据目录，**When** 应用重启，**Then** 日志继续追加到原有文件（不覆盖历史），轮转状态正确恢复。

---

### User Story 3 - Python 命令层日志汇入统一日志流 (Priority: P2)

Python 命令层（`perception_py`，pybind11）产生的日志（含 `logging` 模块输出）与 C++ 日志汇入同一入口、同一文件，遵守同一级别与格式策略，实现"单一脚本化 API"精神下的日志一致性。

**Why this priority**: 命令层是用户交互主路径，其日志若独立于 C++ 日志流，将造成排查断裂与格式割裂；汇入统一流是打通 C++/Python 的诊断闭环。

**Independent Test**: 在 Python 命令层执行一个产生日志的调用（如自定义异常或 info 输出），观察该记录与 C++ 日志出现在同一文件，格式一致（时间戳/级别/来源标识 Python 来源）。

**Acceptance Scenarios**:

1. **Given** Python 命令层通过 `logging` 模块输出日志，**When** 调用触发，**Then** 该记录进入统一日志文件，级别与格式与 C++ 日志一致。
2. **Given** Python 侧写入 ERROR 级日志，**When** 日志写入，**Then** 控制台同步显示错误（该级别开关为开时）。
3. **Given** C++ 与 Python 在相近时间写入日志，**When** 查看日志文件，**Then** 两条记录按时间顺序排列，无格式错乱。

---

### User Story 4 - 菜单栏设置日志级别，即时生效并可持久 (Priority: P2)

用户通过菜单栏 `设置 → 日志级别` 分别勾选控制台与文件的输出级别，无需重启立即生效；重启后设置保持。

**Why this priority**: 级别开关是分级日志的显性控制入口，决定日志体系的实际可用性；菜单栏子菜单为最低成本入口（免对话框/面板），与本条新需求"菜单栏里增加设置日志级别的逻辑"直接对应。

**Independent Test**: 在菜单栏取消勾选控制台的 DEBUG 级别，随后写入一条 DEBUG 日志，控制台不显示、文件侧仍显示；重启应用后勾选状态保持。

**Acceptance Scenarios**:

1. **Given** 菜单栏设置入口可用，**When** 用户勾选/取消某一级别，**Then** 控制台与文件各自按本侧开关矩阵立即过滤，无需重启。
2. **Given** 用户修改过日志级别设置，**When** 应用重启，**Then** 设置保持上次的值（持久化生效）。
3. **Given** VTK 日志开关处于关闭状态，**When** VTK 产生输出，**Then** 该输出不进入统一日志流。（VTK 引入后生效；引入前仅验证开关默认值与配置持久化）

### User Story 5 - 日志路径对用户可见并可一键直达 (Priority: P3)

日志文件写入系统隐藏目录（如 Windows `%APPDATA%\Perception\logs`），用户排障时无从查找。用户应能通过菜单栏看到日志文件完整路径，并一键打开日志所在目录定位 `app.log` 与归档文件。

**Why this priority**: 日志系统的价值在于排障可追溯——若路径对用户不可见，写入即"不可达"，FR-004 的路径约定形同虚设。P3 因其不阻塞其他故事、但为排障闭环的必要补全。

**Independent Test**: 启动应用 → 打开 `设置` 菜单 → 可见"日志文件：<完整路径>"（`%APPDATA%\Perception\logs\app.log`）；点击"打开日志目录" → 系统文件管理器打开 `logs` 目录，可见 `app.log` 及归档。

**Acceptance Scenarios**:

1. **Given** 应用已启动且日志已装配，**When** 用户打开 `设置` 菜单，**Then** 菜单中展示当前日志文件完整路径（只读文本，可选中复制）。
2. **Given** `设置` 菜单展示路径后，**When** 用户点击"打开日志目录"，**Then** 系统文件管理器打开日志所在目录，定位到 `app.log`（及归档）。
3. **Given** 日志路径尚未装配（极端时序），**When** 用户打开 `设置` 菜单，**Then** 路径条目显示占位文本，"打开日志目录"不可用；装配完成后即时更新。

---

### User Story 6 - 文件对话框默认目录跟随启动路径 (Priority: P3)

用户从某目录启动应用（如数据目录 `E:\data`）后，打开文件 / 导出的弹窗初始目录应与启动时的当前路径一致，相对路径解析也以该路径为基准，避免"启动在数据目录、弹窗却固定到家目录"的困惑。

**Why this priority**: 文件对话框与相对路径的可用性依赖启动时的当前工作目录；跟随启动路径使行为自然直观（从哪启动就落在哪），是"打开文件 / 导出"交互的基础一致性。P3 不阻塞其它故事。

**Independent Test**: 在数据目录（如 `E:\data`）以命令行启动 `bin\Release\perception.exe`，打开"打开数据文件"弹窗初始目录为 `E:\data`；导出窗口图片默认保存路径落在 `E:\data`。

**Acceptance Scenarios**:

1. **Given** 应用从某目录启动，**When** 用户打开"打开数据文件"、"导出窗口图片"或"导出 Python 命令"对话框，**Then** 对话框初始目录为启动程序时所在路径（`QDir::current()`）。
2. **Given** 应用已启动且未改变工作目录，**When** 用户以相对路径触发文件保存/截图（如 `--snapshot _shot.png`），**Then** 相对路径解析基准为启动程序时所在路径。

### User Story 7 - 日志路径可配置，切换时迁移旧日志 (Priority: P2)

日志默认写入系统隐藏目录，用户希望将日志集中到自己的工作目录或指定盘符。用户应能通过菜单栏设置日志保存目录：选择新目录后，日志立即写入新路径，且旧路径下的 `app.log` 与归档自动迁移，不丢失历史记录；下次启动仍使用用户设置的路径。

**Why this priority**: 日志文件是排障的第一手材料，路径可配置 + 迁移是日志管理的日常诉求；默认隐藏目录不可见会显著降低可用性。P2 与 US4/US5 共同构成"日志设置"完整入口。

**Independent Test**: 通过 `设置 → 设置日志路径...` 选择新目录后，旧目录的 `app.log`（及轮转归档）出现在新目录，新日志写入新路径；重启应用后仍使用新路径。

**Acceptance Scenarios**:

1. **Given** 应用已启动且日志已装配，**When** 用户通过 `设置 → 设置日志路径...` 选择新目录并确认，**Then** 日志立即写入新路径的 `app.log`，旧路径下的 `app.log` 及全部归档迁移到新目录（旧目录不残留），`设置` 菜单路径展示更新为新路径。
2. **Given** 用户已切换日志路径，**When** 应用重启，**Then** 日志仍写入用户设置的路径（持久化生效）。
3. **Given** 用户选择与当前相同目录，**When** 确认切换，**Then** 不执行重复迁移，路径保持不变。

---

### User Story 8 - 清除历史日志 (Priority: P3)

日志文件随时间增长占用磁盘，用户希望一键清理全部历史日志（含轮转归档）而不影响后续写入。用户应能通过菜单栏执行"清除历史日志"，经确认后清空日志目录，应用继续正常记录新日志。

**Why this priority**: 磁盘空间管理是日志系统的日常运维需求；删除是不可逆操作，必须二次确认。P3 不阻塞其它故事。

**Independent Test**: 日志目录存在 `app.log` 与归档时执行 `设置 → 清除历史日志`，确认后目录中不再存在任何日志文件，应用后续写入正常。

**Acceptance Scenarios**:

1. **Given** 日志目录存在日志文件与归档，**When** 用户点击 `设置 → 清除历史日志` 并确认，**Then** 日志目录中的 `app.log` 及全部归档被删除，后续日志正常写入。
2. **Given** 用户点击"清除历史日志"，**When** 确认对话框弹出，**Then** 用户取消则不做任何删除。

### Edge Cases

- 日志路径不可写（磁盘满、权限不足、目录不存在）时：写入失败不应崩溃应用，应降级为仅控制台输出并给出一次告警，不重复刷屏。
- 多线程/多进程（如 Python 与 C++ 同进程不同线程）同时写入同一文件：单条记录必须原子写入，不允许半行交错。
- 轮转触发瞬间有新写入：不得出现文件句柄泄漏或记录丢失。
- 日志消息含非 ASCII 字符（中文等）：统一按 UTF-8 编码，读写一致无乱码。
- 日志目录被外部删除后应用继续运行：应能重建目录继续写入。
- 超长单条消息：应完整写入或明确截断（带截断标记），不破坏后续记录格式。
- 运行中切换级别开关时正在写入的日志不受影响，开关只对后续记录生效，不丢记录、不产生半行。
- Qt 消息重定向回调中发生嵌套日志（Qt 内部再调用统一 API）：需防递归，最多一层跳转后直通输出。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供统一日志 API（C++ 静态访问入口，如 `Logger::instance()`），支持 INFO/DEBUG/WARN/ERROR/FATAL 级别写入。
- **FR-002**: 系统 MUST 支持每级别独立开关控制输出（DEBUG/INFO/WARN/ERROR/FATAL 各自可开/关），控制台与文件各持一组独立开关矩阵、可分别配置；默认矩阵为 DEBUG 关、INFO/WARN/ERROR/FATAL 开。
- **FR-003**: 系统 MUST 以统一格式输出每条日志：时间戳（本地时间，毫秒精度）、日志级别、来源模块（含 C++ 文件/行或 Python 来源标识）、消息正文，UTF-8 编码。
- **FR-004**: 系统 MUST 支持日志文件路径配置（默认应用数据目录），目录不存在时自动创建，应用重启后追加写入不覆盖。
- **FR-005**: 系统 MUST 按大小轮转日志文件：单文件满 5MB 轮转，保留最近 3 份归档（`app.log`、`app.log.1`、`app.log.2`、`app.log.3`），超出删除最旧。
- **FR-006**: 系统 MUST 将日志实时输出到开发控制台（承载为专属"日志输出"面板，与 Python 控制台 REPL 分离，避免 C++ 日志混入 Python 交互输出），该级别开关为开即显示。
- **FR-007**: 系统 MUST 保证多线程写入线程安全：单条记录原子落盘，无交错截断。
- **FR-008**: 系统 MUST 将 Python 命令层（`perception_py`）产生的日志汇入统一日志流：同一文件、同一级别与格式策略；提供 Python 侧接入机制（logging handler 桥接）。
- **FR-009**: 系统 MUST 在日志写入失败（如路径不可写）时降级为仅控制台输出并告警，不崩溃应用。
- **FR-010**: 系统 MUST 将 Qt 框架自身的日志输出（qDebug/qWarning/qCritical/qFatal）通过消息处理重定向机制纳入统一日志流，遵守统一格式与级别开关。
- **FR-011**: 系统 MUST 为 VTK 日志纳入提供独立开关（默认启用）；关闭后 VTK 输出不再进入统一日志流。**注**：VTK 当前尚未引入项目，本期落地开关配置（`Config.vtkLoggingEnabled`，默认 `true`）与默认值校验；VTK 拦截/桥接实现随后续 render 层引入 VTK 时一并落地。
- **FR-012**: 系统 MUST 在菜单栏提供日志级别设置入口：`设置 → 日志级别 → {控制台 / 文件}` 子菜单，各含 5 个级别复选项（可多选），选择后立即生效、无需重启。
- **FR-013**: 系统 MUST 将日志级别设置持久化（QSettings），应用重启后保持上次配置。
- **FR-014**: 系统 MUST 使日志文件路径对用户可见且可直接访问：`设置` 菜单展示当前日志文件完整路径（只读、可复制），并提供"打开日志目录"动作，一键在系统文件管理器中打开日志所在目录。
- **FR-015**: 系统 MUST 保持进程启动时的当前工作目录不变，并使文件对话框（打开数据文件、导出图片/命令）的默认目录与相对路径解析均以该启动路径（`QDir::current()`）为基准，不固定为家目录或可执行文件目录。
- **FR-016**: 系统 MUST 允许用户通过 `设置 → 设置日志路径...` 更改日志文件路径：选择目录后，日志立即写入新路径，旧日志文件（`app.log` 及归档）自动迁移到新目录，新路径持久化（QSettings），重启后保持。
- **FR-017**: 系统 MUST 提供 `设置 → 清除历史日志` 动作：经用户确认后删除日志目录中的全部日志文件（含归档），并保持后续日志写入正常。

### Key Entities *(include if feature involves data)*

- **LogRecord**: 单条日志记录。属性：时间戳、级别（DEBUG/INFO/WARN/ERROR/FATAL）、来源（模块名/C++ 文件行或 Python 来源）、消息正文。无实现细节，仅数据契约。
- **LogSink**: 日志输出目标。本期含两类：ConsoleSink（开发控制台，承载为独立"日志输出"面板 LogConsoleWidget，与 Python 控制台 REPL 分离）、FileSink（轮转文件）。统一 API 向所有已注册 sink 广播记录。
- **LogLevelMatrix**: 某输出目标的级别开关集合（每级别一个布尔位）；控制台与文件各持一个独立矩阵，运行时可通过菜单栏切换。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 任意模块通过统一 API 写入的日志在控制台与文件两侧均可见，格式字段齐全（时间戳/级别/来源/消息），单条记录 100% 完整写入。
- **SC-002**: 连续写入超过 5MB 日志后，文件侧自动轮转，归档数量稳定为 3 份，磁盘占用 ≤ 当前文件 + 3 归档。
- **SC-003**: 并发 8 线程 × 1000 条日志写入，无交错、无丢失，记录总数精确等于写入总数。
- **SC-004**: Python 命令层产生的日志与 C++ 日志同文件、同格式，时间顺序正确，无乱码（含中文消息）。
- **SC-005**: 日志路径不可用时应用正常运行，仅控制台输出并单次告警，无崩溃、无重复刷屏。
- **SC-006**: 通过菜单栏切换任一级别开关后，控制台与文件立即按各自矩阵过滤（无需重启）；重启后设置保持；VTK 日志开关关闭后 VTK 输出不再进入统一流。
- **SC-007**: 用户可在 `设置` 菜单查看日志文件完整路径，并一键打开日志所在目录定位日志文件与归档（FR-014）。
- **SC-008**: 文件对话框（打开数据文件/导出图片/导出命令）初始目录与相对路径解析基准均为启动程序时所在路径，而非固定家目录或 exe 目录（FR-015）。
- **SC-009**: 通过 `设置 → 设置日志路径...` 切换后，旧目录的 `app.log` 与归档全部迁移到新目录（旧目录不残留），后续日志写入新路径，重启后仍使用新路径（FR-016）。
- **SC-010**: 执行 `设置 → 清除历史日志` 后，日志目录中不再存在任何日志文件与归档，且后续日志正常写入（FR-017）。

## Assumptions

- 日志默认路径为应用数据目录（随平台约定，如 Windows `%APPDATA%`），可通过配置覆盖。
- 默认级别矩阵为 DEBUG 关、INFO/WARN/ERROR/FATAL 开；控制台与文件各自独立配置。
- 本期范围：后端基础设施 + 菜单栏日志级别设置入口（`设置 → 日志级别`）+ 日志路径管理（`设置` 菜单展示路径、"打开日志目录"、"设置日志路径..." 切换时迁移旧日志、"清除历史日志"）；应用内日志查看/过滤 UI 面板明确**不在本期**，作为后续独立功能（路径管理仅指"可见 + 可打开目录 + 可配置 + 可清除"，不构成查看面板）。开发控制台承载的"日志输出"面板（LogConsoleWidget）仅作实时只读输出、不含过滤/搜索/历史检索，**不构成**上述"日志查看面板"，故不越界。
- 日志路径可由用户运行期配置（`设置 → 设置日志路径...`），切换时自动迁移旧日志文件；默认路径由应用装配层注入，与 Logger 实际写入路径保持一致。
- 日志方案采用标准机制：日志核心基于 C++ 标准库实现，**不使用 Qt 日志工具类**（QDebug/QLoggingCategory/qInstallMessageHandler 仅用于捕获 Qt 自身输出，不作日志实现）；Python 侧基于标准 `logging`。
- 菜单栏级别设置持久化采用 QSettings，重启保持（若希望每次启动重置，需显式调整 FR-013）。
- 菜单栏入口挂载于现有菜单栏（无"设置"菜单时新增顶层"设置"菜单），具体位置在计划阶段按现有菜单结构确定。
- Python 命令层与 C++ 运行于同一进程（pybind11 嵌入式解释器），跨进程日志分发不在本期。
- 轮转策略固定为大小轮转（5MB × 3 份）；按日期轮转等其他策略不在本期。
- 开发控制台的承载为独立"日志输出"面板（LogConsoleWidget：底部与 Python 控制台同 tab 组、默认隐藏，`视图 → 日志输出` 或 `Ctrl+3` 打开），与 Python 控制台（REPL）职责分离：REPL 仅显示 Python 交互输出（print/异常 traceback），统一日志流（C++ / Python logging / Qt 重定向）全部进入日志输出面板；复用现有错误展示样式（ERROR 级红色高亮）。
- VTK 当前未引入项目（render 层仅为 CMake 骨架，CMake 中已声明 `find_package(VTK)` 但仅在 `PERCEPTION_BUILD_GUI` 打开时启用）：本期不链接 VTK、不编写 VTK 拦截代码；`vtk_log_bridge` 与拦截验证随后续引入 VTK 时落地（FR-011 开关配置与取值本期即生效并持久化）。
